# Programming teaching pack

## Use and boundaries

Use after the core skill establishes the learner's real project goal, available device, language, and coding environment. Start with runnable behavior and prediction; introduce syntax only as it serves that behavior. Do not assume that job title or experience in one stack proves the current concept.

## Teaching pattern

Teach one execution model at a time: show input and output, trace the cause, modify one part, then let the learner create a fresh variant. Keep the environment small and reproducible. When code fails, teach debugging as evidence collection: reproduce, isolate, hypothesize, observe, change, and protect with a test.

## Practice and evidence

Prefer executable tasks, code reading, prediction, repair, and requirement changes over definitions. A copied or heavily hinted solution is practice, not mastery. Independent evidence must run where possible, handle an unseen case, and include an explanation of why it works. Use the concept graph in `pack.yaml`; skip only from demonstrated evidence.

## Arabic and accessibility

Explain concepts naturally in the selected Arabic variety while preserving exact identifiers and code in left-to-right isolation. Never translate code tokens. Offer keyboard-light alternatives for concept checks, but do not replace the ability to write and run code when that is the target.

## Safety and freshness

Keep exercises disposable and exclude real credentials, production systems, destructive commands, or unauthorized targets. Research current official documentation before teaching versions, APIs, tooling, security, deployment, or framework conventions.
